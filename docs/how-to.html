How to clear the WordPress cache in WordPress

Clearing the cache means deleting the stored HTML so the next request is rendered from scratch. In Meridian Press Cache that is one button on the dashboard, but the reason a clear sometimes appears to do nothing is worth knowing: a page cache sits in front of PHP, so a cleared page is rebuilt on the next visit, and any CDN or proxy in front of the site keeps its own copy. Clearing twice in a row without a visit does not produce a different result.

Clearing one page instead of everything

A full purge is the safe habit during development and the wrong habit in production: every purge means the next visitor pays the render cost. Meridian Press Cache purges the URL that changed when a post is edited, and the whole cache only when you press the button or change a setting that affects every page, such as minification.

The three caches people confuse

WordPress has a page cache, an object cache and whatever your host put in front of the site. A page cache stores finished HTML. An object cache stores query results for reuse inside one request or across requests if a persistent backend exists. A host-level cache stores everything at the edge and is usually cleared from a hosting panel, not from WordPress. Meridian Press Cache manages the first and exposes counters for both.

If a change does not appear after clearing, check in that order: page cache, object cache, host cache. Most 'the plugin broke my site' reports end at step three.

When the cache should stay warm

On a shop, a purge during a sale is a self-inflicted slowdown: the first hundred visitors after a full purge all render. Configure purge-on-update for content pages, leave the product archive cached, and watch the hit rate on the dashboard for a day before deciding it is broken.

Watch the ratio rather than the total: hits divided by requests, over a day. A cache that serves 60% of requests is doing something; 95% means it is covering the site. The same screen shows cache size and the oldest entry, which tells you whether the TTL matches how often the content actually changes.

If the ratio is high and the site still feels slow, the problem is downstream of PHP: images, fonts, or a host network that is saturated. That is the point at which a CDN becomes the right answer, and the counters here are how you know you have reached it.

Who this is for

Meridian Press Cache fits a site on one server: a blog, a brochure site, a small shop, a club site with a thousand visits a day. It is the wrong tool for a WordPress network of fifty sites with a shared object cache cluster — that needs infrastructure, not a plugin — and it is unnecessary on a site that already serves static files from a build step.

What it does not do

No CDN. No image CDN. No edge computing, no page builder, no backup, no security firewall. Meridian Press Cache does not rewrite your theme, does not inject a dashboard banner asking for a review, and does not phone home unless the administrator ticks the box on the dashboard. If a feature needs a remote service to work, it does not belong in a cache plugin.

Frequently asked

Does clearing the cache delete my content?

No. It deletes generated HTML and stored counters. Posts, pages, media and settings are untouched; the next request regenerates the page.

Why is the site slower right after a purge?

Every cached page has to be rendered again. The first visitors after a purge pay that cost; the hit rate recovers as pages are visited.

Should I clear the cache after publishing a post?

Meridian Press Cache purges the affected URL automatically on save, so a manual purge is only needed after changing a global setting.
